# 前端优化建议

记录日期：2026-05-03

## 审阅范围

本次先做前端代码、样式和交互层面的体验审阅，主要依据：

- `frontend/src/App.tsx`：2529 行，包含工作台布局、全部模块渲染、数据请求状态、地图初始化和主要交互。
- `frontend/src/App.css`：1083 行，包含主题变量、布局、卡片、地图、圈人中心和大屏样式。
- `frontend/src/api.ts`：449 行，集中定义接口类型与请求封装。
- `frontend/src/App.test.tsx`：已有 3 个前端回归测试。
- `docs/圈人中心加载缓慢优化计划.md`：圈人中心慢加载的专项背景。

验证情况：

- `npm --prefix frontend run build` 通过。
- `npm --prefix frontend run test` 通过，3 个测试全部通过。
- 构建产物提示较大 chunk：`maplibre` 约 1024KB，`charts` 约 370KB，后续需要纳入首屏性能优化。

## 当前前端现状

项目是一个 React + Vite 单页工作台，当前模块包括：

- 资产门户
- 总览
- 热力回放
- 路径对比
- 推荐中心
- 圈人中心
- 答辩大屏

已有基础比较扎实：

- 使用 CSS 变量实现浅色/深色主题。
- MapLibre 已使用动态 `import("maplibre-gl")`，不是直接同步加载地图 JS。
- `vite.config.ts` 已手动拆出 `react`、`charts`、`maplibre` chunk。
- 圈人中心已经有分区 loading、标签结果缓存、`AbortController` 取消过期请求、道路几何按需加载，这与慢加载优化计划方向一致。
- 测试中已 mock MapLibre 和 API，具备继续扩展交互测试的基础。

主要问题集中在：

- `App.tsx` 过大，业务模块、请求状态、地图逻辑和 UI 渲染耦合。
- 地图展示仍嵌在热力/路径等业务模块中，后续必须独立渲染，业务模块只能通过数据和事件驱动地图。
- 部分首屏和模块切换请求较早发生，缺少按模块懒加载策略。
- 样式层级偏重，卡片、边框和阴影较多，信息密度有了，但视觉主次还可以更清楚。
- 地图、热力回放、路径表单、推荐表单、圈人中心的交互反馈还可以更细。
- 移动端和可访问性目前只是基本可用，还没有达到稳定产品体验。

## P0：优先优化建议

### 1. 拆分 `App.tsx`，降低后续体验迭代成本

当前全部业务集中在 `App.tsx`，已经超过 2500 行。继续在这个文件上叠交互会越来越难维护，也会让体验优化容易互相影响。

建议拆分：

- `components/layout/WorkbenchLayout.tsx`：侧边栏、状态面板、主题切换、内容框架。
- `features/assets/AssetPortal.tsx`
- `features/overview/OverviewPanel.tsx`
- `features/heatmap/HeatmapPanel.tsx`
- `features/route/RoutePanel.tsx`
- `features/recommend/RecommendPanel.tsx`
- `features/crowd/CrowdPanel.tsx`
- `features/bigscreen/BigScreenPanel.tsx`
- `features/map/MapDisplay.tsx`
- `features/map/mapLayers.ts`
- `hooks/useMetaData.ts`
- `hooks/useCrowdData.ts`
- `hooks/useRouteQuery.ts`
- `hooks/useMapLibre.ts`

预期收益：

- 每个模块可以独立优化 loading、空状态、错误提示和测试。
- 路径表单、地图、列表、KPI 等可复用组件能自然抽出来。
- 后续加动效、筛选、分页、虚拟列表时不会继续撑大单文件。

### 2. 把全局 loading/error 改成模块级状态

当前存在一个全局 `loading` 和 `error`。问题是任意接口失败都会显示在主内容顶部，用户切到别的模块后也可能看到不相关错误。

建议改为：

- `overviewStatus`
- `metaStatus`
- `heatmapStatus`
- `routeStatus`
- `recommendStatus`
- `crowdVehiclesStatus`
- `crowdSegmentsStatus`
- `crowdGeometryStatusByRoadId`

每个状态至少包含：

```ts
type LoadState<T> = {
  data: T;
  loading: boolean;
  error: string | null;
  updatedAt?: string;
};
```

交互上：

- 当前模块只展示自己的错误。
- 顶部可以保留一个“系统状态”摘要，但不要吞掉模块内错误。
- 标签切换、热力桶切换时保留旧数据，并显示“正在更新”，避免列表突然清空。

### 3. 首屏请求和大包加载按模块延迟

现在进入应用后会立即加载总览、元数据、圈人汇总、路径能力等。对工作台来说，首屏应该优先保证当前模块可操作，其它模块可以空闲预取或点击后加载。

建议：

- 默认只加载当前首屏必需数据。
- 圈人中心、推荐中心、路径能力检查可以在用户点击相关模块时加载；也可以在 `requestIdleCallback` 里低优先级预取。
- `recharts` 相关代码从 `App.tsx` 顶层移入 `OverviewPanel`，必要时用 `React.lazy`。
- 地图 CSS 和地图组件一起懒加载，避免非地图模块也承担地图样式成本。
- 如果默认首屏仍是“总览”，图表可以保留首屏加载；但 MapLibre 应确保只在进入热力/路径模块后加载。

验收目标：

- 非地图首屏不主动执行地图初始化。
- 初始可交互时间明显优先于地图与推荐模块准备。
- 构建警告中的大 chunk 不再影响所有用户的首屏路径。

### 4. 地图展示模块必须独立渲染

这是后续前端重构的硬性约束：地图展示模块必须独立渲染，不能和热力回放、路径对比、圈人中心等业务模块耦合渲染。

建议边界：

- `MapDisplay` 独立负责地图 DOM、MapLibre 实例生命周期、resize、销毁、底图加载状态。
- 业务模块不直接渲染 `.map-canvas`，也不直接调用 `map.addLayer`、`map.getSource`、`setLayoutProperty`。
- 热力、路径、圈人只生成地图展示所需的数据描述，例如 `heatmapFeatures`、`routeFeatures`、`focusedRoadGeometry`、`viewportBounds`。
- 图层注册和更新集中放在 `features/map/mapLayers.ts` 或 `useMapLayers`，按 `mode` 决定加载热力层、路径层、选点层。
- 业务模块和地图之间通过 props、context 或轻量 store 通信，例如：

```ts
type MapDisplayMode = "heatmap" | "route" | "crowd-focus";

type MapDisplayState = {
  mode: MapDisplayMode;
  heatmap?: HeatmapLayerState;
  route?: RouteLayerState;
  focusBounds?: MapBBox | null;
  pickMode?: "none" | "start" | "end";
};
```

交互原则：

- 路径模块可以订阅地图点击事件，但地图点击事件先由 `MapDisplay` 统一处理，再回调 `onPickPoint`。
- 圈人中心点击“定位到热力图”只更新地图状态和模块跳转，不直接操作地图实例。
- 热力回放切换时间桶只更新图层数据，不重新挂载地图。
- 地图可作为独立工作区区域存在，也可以被页面布局引用，但渲染生命周期不能跟单个业务面板强绑定。

预期收益：

- 避免地图实例在模块切换时反复创建、销毁或错绑容器。
- 热力、路径、圈人后续新增图层时不会互相污染。
- 地图加载、瓦片失败、空图层、选点状态可以统一处理。
- 单元测试可以 mock `MapDisplay`，业务模块测试不再依赖 MapLibre。

### 5. 圈人中心继续补齐“快感”交互

专项计划里的核心后端/接口优化已经有前端适配痕迹：`/crowd/segments` 默认 `include_geometry=false`，点击单条道路再加载几何，这个方向正确。

建议继续补：

- 标签切换时保留上一标签结果，面板头部显示“正在加载新标签”，不要先清空列表。
- 车辆样本和道路热点分别显示局部骨架屏，避免用户以为整个页面卡住。
- `定位到热力图` 和 `设为路线终点` 使用单行按钮级 loading，当前代码已有 `crowdGeometryLoadingRoadId`，后续可扩展成 `Set<roadId>`，支持多个道路并发。
- 对已访问过的标签加“已缓存”或“已更新于 xx:xx”的轻量提示。
- 默认预取前 2 个高频标签的热点列表，提升课堂演示和常用路径体验。

## P1：交互与视觉体验建议

### 6. 路径对比与推荐中心共用路线查询表单

路径对比和推荐中心都维护同一组输入：

- 起始时间
- 查询时间
- 起点纬度/经度
- 终点纬度/经度

建议抽成 `RouteQueryForm`，并补齐：

- 经纬度范围校验。
- `datetime-local` 为空或格式异常时的 inline error。
- “使用地图选择起点/终点”的状态在两个模块间一致。
- 按钮禁用时显示原因，例如“路径能力未就绪”或“请选择查询时间”。
- 输入修改后提示结果已过期，避免用户误以为旧路径结果对应新参数。

### 7. 热力回放交互改成时间轴

当前热力回放用数字输入控制 `bucketIndex`，用户需要理解“桶索引”，不够直观。

建议：

- 改成时间轴 slider，展示当前桶时间，如 `08:00`。
- 增加播放速度：`0.5x / 1x / 2x`。
- 日期切换时自动暂停播放并重置到第一个时间桶。
- 当前桶加载中时，在地图右上角显示轻量状态。
- 显示当前桶道路数、最大流量、总流量，帮助用户判断画面是否加载完整。
- “缩放到框选范围”不要使用固定坐标，后续应改成地图绘制框选或预设范围菜单。

### 8. 地图图层按场景注册

当前初始化地图时会同时创建热力、最短路径、最快路径、起终点等 source/layer，再通过 visibility 控制。这能工作，但初始化成本和心智成本都偏高。

建议：

- `createBaseMap()` 只负责底图。
- `attachHeatmapLayers(map)` 只在热力模块调用。
- `attachRouteLayers(map)` 只在路径模块调用。
- 上述函数只能被独立的 `MapDisplay` / `useMapLayers` 调用，业务面板不直接持有 MapLibre 实例。
- 地图容器首次进入时显示“地图加载中”，瓦片失败时显示可恢复提示。
- 路线和热力 GeoJSON 解析量变大时，考虑把 WKT/GeoJSON 转换移到后端或 Web Worker。

### 9. 视觉层级从“卡片堆叠”改成“工作台层级”

当前界面卡片、边框、阴影、渐变比较多。对数据工作台来说，重点是扫描效率，建议更克制：

- 主内容区域保留一个页面容器即可，内部面板减少阴影。
- KPI 卡片可以保留，但图表区和列表区尽量用分隔线、留白、标题层级表达。
- `body` 背景的径向渐变可以弱化或移除，避免操作型界面显得装饰过重。
- 当前配色以蓝/青为主，建议加入更稳定的语义色：成功绿、告警橙、风险红、普通灰，避免所有状态都像同一种高亮。
- `nav-icon` 现在是 `AS/OV/HM` 文本缩写，建议用 `lucide-react` 图标提升识别速度。
- `button` 的全局 `margin-bottom: 10px` 容易影响 flex/grid 中的按钮对齐，应改为在需要堆叠的局部类上控制间距。
- CSS 里声明了 `Sora` 和 `Manrope`，但项目没有看到字体加载；要么正式引入字体，要么使用系统字体并删除无效字体名。

### 10. 移动端布局需要单独设计

当前 960px 以下基本是所有 grid 变单列，能响应，但不够像一个专门设计过的移动体验。

建议：

- 小屏下把左侧导航变成顶部模块切换条或下拉菜单，避免用户先滚过整块 sidebar。
- 地图高度从固定 `520px` 改成 `min(60vh, 520px)`，小屏下避免地图压住所有操作。
- 路径边明细在移动端改成卡片或可横向滚动表格，不要直接隐藏为 3 列后丢失距离/耗时上下文。
- 圈人中心标签条使用横向滚动，并固定在当前模块顶部。
- 增加 `max-width: 640px` 的细粒度规则，专门处理按钮、表单和地图。

## P2：可访问性与稳定性建议

### 11. 补齐键盘和读屏语义

建议优先补这些低成本项：

- 当前导航按钮增加 `aria-current="page"` 或 `aria-pressed`。
- 主题按钮、图层显隐、播放/暂停增加明确的 `aria-pressed`。
- 错误提示使用 `role="alert"`。
- 加载状态使用 `role="status"` 和 `aria-live="polite"`。
- 地图容器提供可读说明，例如当前点位、当前图层和可用替代操作。
- 增加 `:focus-visible` 样式，确保键盘用户知道焦点在哪里。
- 图例不要只依赖颜色，最短/最快路线已经有文字说明，后续图上样式也应保证虚线/实线差异明显。

### 12. 请求封装要处理非 JSON 和网络失败

`api.ts` 里的 `request` 默认执行 `res.json()`。如果后端返回非 JSON 错误、204、代理错误页或网络断开，错误信息会不够稳定。

建议：

- 先读取 `content-type`，JSON 才解析 JSON。
- 捕获 `fetch` 网络错误，转换成用户可理解文案。
- 支持超时和 `AbortSignal`。
- 对 GET 请求增加可选去重，避免 React StrictMode 开发环境重复请求干扰性能观察。

### 13. 扩展测试覆盖到关键体验

当前测试主要覆盖：

- 总览基础渲染。
- 路径对比结果。
- 箱线图 hover 提示。

建议新增：

- 圈人中心切换标签时，会取消旧请求并使用缓存。
- 道路热点几何点击后才请求。
- 热力图日期/时间桶切换时会更新地图数据。
- 路径能力未就绪时按钮禁用且提示明确。
- 推荐中心生成中按钮 loading 正确。
- `role="alert"` 和 `role="status"` 可被测试捕获。

后续可以增加 Playwright 冒烟用例：

- 进入总览。
- 切换热力回放并播放。
- 切换路径对比并地图选点。
- 切换圈人中心并定位道路。
- 进入答辩大屏并切换全屏。

## P3：后续产品化建议

### 14. 建立轻量组件和设计规范

不建议一开始引入很重的 UI 框架，但可以沉淀自己的基础组件：

- `Button`
- `IconButton`
- `SegmentedControl`
- `StatusPill`
- `MetricCard`
- `PanelHeader`
- `EmptyState`
- `InlineError`
- `SkeletonBlock`
- `RouteQueryForm`
- `MapDisplay`

配套约束：

- 卡片半径控制在 8px-12px，避免全部区域都像浮层。
- 按钮区分 primary / secondary / ghost / danger。
- 所有状态色用 token 管理，不在业务 CSS 里散落硬编码颜色。
- 表格/列表统一密度、行高和 hover 样式。

### 15. 主题偏好和大屏模式持久化

建议：

- 主题默认跟随 `prefers-color-scheme`。
- 用户切换主题后写入 `localStorage`。
- 答辩大屏的自动轮播开关、当前 slide 可保留在本地状态。
- 全屏失败时给出提示，而不是只切换本地 focus 状态。

### 16. 删除模板遗留和无用资产

项目里还有 `frontend/src/assets/vite.svg`。如果没有使用，可以删除，减少模板痕迹。

## 推荐落地顺序

1. P0：拆 `App.tsx`，先按模块迁移，不改视觉。
2. P0：全局 loading/error 改成模块状态，保留旧数据更新。
3. P0：抽出独立 `MapDisplay`，地图 DOM、实例生命周期和图层更新不能放在业务模块里。
4. P0：确认 MapLibre 和推荐/圈人请求只在需要时加载或空闲预取。
5. P1：抽 `RouteQueryForm`，统一路径和推荐输入体验。
6. P1：热力回放改成时间轴和局部 loading。
7. P1：收敛卡片、阴影、按钮 margin 和移动端导航。
8. P2：补可访问性语义和关键交互测试。
9. P3：沉淀轻量设计组件和主题持久化。

## 验收标准

- 首页进入后无长时间空白，当前模块数据有明确 loading 和错误反馈。
- 切换模块不出现不相关错误残留。
- 非地图模块不初始化 MapLibre 地图实例。
- 业务模块不直接渲染地图容器、不直接调用 MapLibre API，只向独立地图展示模块传入展示状态。
- 热力图、路径图层、圈人道路定位可以共用同一个地图展示边界，但各自图层状态互不污染。
- 圈人中心标签切换时列表不闪空，旧数据可见，新数据状态明确。
- 热力回放时间桶操作能用时间理解，不需要用户理解索引。
- 路径对比和推荐中心输入一致，错误提示靠近字段。
- 移动端打开后不需要先滚完整个 sidebar 才能看到内容。
- `npm --prefix frontend run build` 和 `npm --prefix frontend run test` 持续通过。
- 关键交互至少覆盖单元测试，后续补一条浏览器冒烟链路。

## 一句话结论

当前前端已经能完整承载业务演示，但优化重点不应先做“更花的视觉”，而是先把巨型 `App.tsx` 拆开、把请求状态局部化、让地图展示模块独立渲染，并让图表/圈人数据按场景加载，再用更克制的工作台样式提升扫描效率。这样体验会变快，代码也会更容易继续迭代。
