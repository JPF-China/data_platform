# 圈人中心加载缓慢优化计划

记录日期：2026-05-03

## 现象

圈人中心页面进入或切换标签时，车辆样本加载较快，但道路热点列表明显卡顿。红框中的标签点击后，会联动请求车辆样本和道路热点数据，因此用户感知为“圈人中心整体加载慢”。

## 当前实测

| 接口 | 典型耗时 | 说明 |
| --- | ---: | --- |
| `/api/v1/crowd/profile-summary` | 约 0.16s | 标签汇总，基本正常 |
| `/api/v1/crowd/vehicles?tag_code=...&limit=12` | 约 0.04s - 0.08s | 车辆样本，基本正常 |
| `/api/v1/crowd/segments?tag_code=...&limit=8` | 约 11s - 18s | 主要慢点 |

补充数据：

- `trip_segments` 约 45,903,183 行，总大小约 30GB。
- `/crowd/segments` 单次返回体可达约 8MB - 68MB。
- 每次只返回 8 条道路热点，但后端会为这些道路现场聚合大量轨迹段几何。

## 根因

### P0：道路热点接口实时聚合几何

位置：`backend/app/services/crowd_service.py`

当前 `/crowd/segments` 会从 `ads_vehicle_segments` 取热点道路后，再关联 `trip_segments` 聚合道路几何：

```sql
ST_AsGeoJSON(ST_Multi(ST_LineMerge(ST_Collect(s.path_geom))))
```

这会导致：

- 查询需要扫描/读取大量 `trip_segments` 数据。
- `ST_Collect`、`ST_LineMerge`、`ST_AsGeoJSON` 在请求时实时计算，CPU 和内存开销大。
- 返回 GeoJSON 体积过大，网络传输和浏览器 JSON 解析也慢。

### P1：开发模式下接口重复请求

位置：`frontend/src/main.tsx`

当前前端使用 React `StrictMode`，开发模式下 `useEffect` 会重复执行，后端日志中可见部分接口重复请求两次。这不是根因，但会放大慢感。

### P1：圈人数据加载没有细分 loading 状态

位置：`frontend/src/App.tsx`

当前圈人中心同时加载车辆样本和道路热点。道路热点慢时，用户容易误以为整个模块卡住。

## 优化事项

### 1. 拆分道路热点列表和几何加载

优先级：P0

目标：

- `/crowd/segments` 默认只返回列表字段，不返回 `geometry`。
- 列表字段包括 `road_id`、`road_name`、`trip_count`、`vehicle_count`、`distance_m`、`avg_speed_kmh` 等。
- 点击“定位到热力图”或需要地图展示时，再单独请求某条道路的几何。

建议接口：

- `GET /api/v1/crowd/segments?tag_code=xxx&limit=8&include_geometry=false`
- `GET /api/v1/crowd/segments/{road_id}/geometry`

预期收益：

- 圈人中心首屏加载从 10 秒级降到 1 秒内。
- 避免每次标签切换都下载几十 MB GeoJSON。

### 2. 预聚合道路几何读模型

优先级：P0

目标：

- 新增道路几何读模型表，避免请求时从 `trip_segments` 实时聚合。
- 几何可以按 `road_id` 预先合并、简化，并存储为 GeoJSON 或 PostGIS geometry。

建议表：

```sql
CREATE TABLE IF NOT EXISTS ads_road_geometry (
  road_id text PRIMARY KEY,
  road_name text,
  geometry geometry(MultiLineString, 4326),
  geometry_geojson text,
  simplified_geojson text,
  source_segment_count bigint,
  updated_at timestamptz NOT NULL DEFAULT now()
);
```

建议处理：

- 入仓或统计刷新阶段生成。
- 使用 `ST_LineMerge(ST_Collect(...))` 离线计算。
- 使用 `ST_SimplifyPreserveTopology` 生成轻量版几何。
- 圈人中心优先读取 `simplified_geojson`。

预期收益：

- 将实时重计算改为读缓存。
- 大幅降低数据库 CPU、IO 和临时文件开销。

### 3. 给热点表增加排序索引

优先级：P1

目标：

- 加速 `ads_vehicle_segments` 按标签取 Top N。

建议索引：

```sql
CREATE INDEX IF NOT EXISTS idx_ads_vehicle_segments_tag_rank
ON ads_vehicle_segments (tag_code, trip_count DESC, distance_m DESC, road_id);
```

说明：

- 当前真正慢点在几何聚合，但该索引可以减少热点 Top N 排序成本。
- 适合作为低风险补充优化。

### 4. 优化车辆样本查询

优先级：P2

目标：

- 当前车辆样本查询已较快，但仍可避免每次全量聚合车辆标签。

建议：

- 将车辆标签数组预聚合到 `tdm_vehicle_profile` 或新增读模型。
- 或改写 SQL，只对命中的 `limit` 车辆再聚合标签。

预期收益：

- 当前收益有限，主要作为后续扩展。

### 5. 前端增加分区 loading 和缓存

优先级：P1

目标：

- 车辆样本和道路热点分别显示 loading。
- 标签切换时缓存已加载过的结果，避免重复请求。
- 请求被新标签覆盖时取消旧请求，避免旧响应回写。

建议实现：

- 增加 `crowdVehiclesLoading`、`crowdSegmentsLoading`。
- 使用 `Map<tagCode, CrowdVehicle[]>` 和 `Map<tagCode, CrowdSegment[]>` 做内存缓存。
- 使用 `AbortController` 取消过期请求。

预期收益：

- 用户能看到车辆样本先出来。
- 快速切换标签时不会堆积慢请求。

### 6. 开发环境重复请求治理

优先级：P2

目标：

- 保留生产环境行为不变。
- 降低开发联调时的重复请求干扰。

可选方案：

- 接受 React `StrictMode` 的开发行为，仅在分析性能时注意排除。
- 或在圈人请求层增加缓存/去重，同一 `tag_code` 的并发请求复用同一个 Promise。

## 推荐落地顺序

1. 先改 `/crowd/segments`：默认不返回 geometry。
2. 前端道路热点列表适配无 geometry 返回，点击定位时再加载几何。
3. 新增 `ads_road_geometry` 读模型和刷新脚本。
4. 接入简化几何，替代实时 `ST_Collect`。
5. 增加热点排序索引。
6. 增加前端缓存、分区 loading 和请求取消。

## 验收标准

- 进入圈人中心首屏接口总耗时小于 1 秒。
- 标签切换后车辆样本和道路热点文本列表小于 1 秒返回。
- 点击单条道路定位时，几何加载小于 2 秒。
- `/crowd/segments` 默认响应体控制在 100KB 以内。
- 后端日志中同一标签切换不再产生重复慢查询。
- 浏览器切换标签时页面不冻结、不长时间空白。

## 备注

当前问题的核心不是车辆样本或标签数量，而是道路热点接口把大体积几何计算和列表查询绑在一起。优先拆分“列表数据”和“地图几何”，收益最大、改动边界也最清晰。
